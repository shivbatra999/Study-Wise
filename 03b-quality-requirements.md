# 03b - Quality Requirements

## Purpose and scope

Study-Wise is a local-first study assistant that imports course PDFs and
PowerPoint presentations, answers questions using the imported material, and
generates practice quizzes through a local language model served by Ollama.
These requirements define the quality expected of the planned application;
they do not claim that the current repository implements or meets them.

The targets below are proposed acceptance criteria for the course project.
The team will confirm feasibility during its initial prototype and record any
approved changes, with reasons, before final validation.

## Validation conditions

- Record the operating system, CPU, RAM, available storage, software versions,
  Ollama model and model settings with every performance report. Select a
  shared reference laptop with at least 16 GB RAM and SSD storage during the
  first milestone; a dedicated GPU must not be required for acceptance.
- Use a fixed, shareable test corpus of text-based PDFs and `.pptx` files from
  synthetic or permission-cleared material. Include a 50-page PDF, a 50-slide
  presentation, an empty file, a corrupt file, and an image-only PDF. OCR and
  legacy `.ppt` support are outside the initial acceptance scope.
- Time ingestion from selecting a valid file until it is available for search.
  Time answers and quizzes from submission until the complete result appears.
  Report cold model startup separately from warm model inference.
- Run each timed scenario five times under the same conditions. Every run must
  meet its stated limit; retain all results rather than only the fastest run.
- Store repeatable test steps, observations and pass/fail evidence with the
  project. A requirement passes only when all of its acceptance criteria pass.

## Requirements and acceptance criteria

| ID | Quality attribute | Requirement and measurable target | Verification |
| --- | --- | --- | --- |
| QR-01 | Privacy and offline operation | After dependencies and the selected model are installed, importing, indexing, asking questions and generating quizzes must work with external network access disabled and loopback networking available. Course content, prompts and answers must never be sent outside the device. | Complete each core workflow offline. Repeat with external networking available while monitoring application traffic; verify that model requests use only the local Ollama endpoint and no content leaves the device. |
| QR-02 | Local access protection | Application and model services must bind to loopback by default. Document bodies, prompts and answers must be excluded from routine diagnostic logs. | Inspect default configuration, inspect listening addresses, attempt a connection from another device on the same network, and check logs generated by representative workflows. Local requests must succeed, remote requests must fail, and logs must contain no study content. |
| QR-03 | Data removal | Removing a document must remove its application-managed original or copy, extracted text, indexed chunks and embeddings. Removing a course must also remove its saved questions, answers and quizzes. The user's source file outside application storage must remain untouched. | Delete a document and then a course, restart the application, inspect application storage, and search for distinctive test text. Deleted records must be absent and unavailable for retrieval; verify that the external source file still exists. This is logical deletion, not a claim of secure disk erasure. |
| QR-04 | Document processing | Valid text-based PDFs and `.pptx` files up to 20 MB and 100 pages or slides must either import successfully or report a specific recoverable error. Unsupported, empty, corrupt and image-only files must receive an explanatory message and must not appear as successfully indexed. | Import fixtures at the supported limits and each invalid fixture. Confirm that successful imports are searchable, failures leave no partial searchable index, and a valid import still works after each failure. |
| QR-05 | Ingestion performance | On the reference laptop, each standard 50-page PDF and 50-slide presentation, at most 10 MB each, must become searchable within 120 seconds. The interface must acknowledge the import within 1 second and show a processing state until completion or failure. | Run the timed ingestion scenarios using a fresh index for each run. Record total time and observe acknowledgement and processing feedback. |
| QR-06 | Generation performance | With the selected model already loaded, an answer of at most 200 words must complete within 60 seconds, and a five-question quiz must complete within 120 seconds. The interface must show a working state within 1 second. | Run the fixed prompt set under the recorded model configuration. Record complete-result latency and inspect the working state; report cold-start timing separately. |
| QR-07 | Grounded answers | Answers must cite the source document and page or slide for factual claims derived from course material. On a reviewed set of 20 answerable questions, at least 18 answers must be correct and supported by the cited passages. On 5 questions absent from the corpus, all 5 responses must explain that the supplied material is insufficient rather than inventing an answer. | Two teammates independently compare each answer and citation with the source. An answer passes only if it is correct, its citations resolve, and the passages support its claims; resolve disagreements against the source and retain the scoring record. |
| QR-08 | Quiz quality | Each requested five-question quiz must contain five distinct questions, a correct answer or answer key, an explanation, and a source reference for each question. Multiple-choice questions must have exactly one correct option. At least 23 of 25 questions across five fixed quiz requests must be accurate, unambiguous and supported by their sources. | Two teammates review all 25 questions against the material. Check the structural rules for every quiz and score factual correctness separately. |
| QR-09 | Reliability and recovery | Imported material must remain searchable after a normal restart. A failed import, unavailable Ollama service, or interrupted generation must not corrupt previously saved material. Model requests must time out within 180 seconds and show a recovery action. | Restart after a successful import, interrupt a later import, stop Ollama during generation, and simulate an unresponsive request. Confirm that existing material remains usable, errors are visible, partial output is not saved as complete, and retry works after the cause is resolved. |
| QR-10 | Usability | At least 4 of 5 student testers unfamiliar with the interface must import a file, ask a question and generate a quiz without facilitator assistance within 10 minutes, excluding installation and model download. | Use the same task script for each tester. Record task completion, elapsed time and points of confusion without supplying instructions during the trial. |
| QR-11 | Keyboard access and readability | The import, question and quiz workflows must be usable with only a keyboard. Controls must have descriptive accessible names, visible focus indicators and no keyboard traps. At 200% browser zoom, essential controls and content must remain available without overlap. | Walk through each core workflow with the keyboard, inspect control names using browser accessibility tools, and repeat at 200% zoom. Record and resolve any blocked action. |
| QR-12 | Maintainability and reproducibility | A teammate must be able to install and launch the application on a clean environment using the documented setup steps, dependency declarations and selected model instructions. Automated checks must cover ingestion failures, retrieval behavior, quiz structure and unavailable-model handling. | Have someone other than the setup author follow the instructions, record missing steps, and run the documented checks. All required checks must pass before merging a release candidate. |

## Acceptance and traceability

The final validation report will list each requirement ID, the tested revision,
environment, result and evidence location. QR-01 through QR-04 and QR-09 are
release blockers because they protect local data and core operation. Any other
unmet target must also be corrected or explicitly revised by the team before
the release is considered accepted; it must not be silently marked as passed.

The implementation sequence and risks that may prevent these targets from
being met are tracked in [04a - Team Plan and Risks](04a-team-plan-risks.md).
